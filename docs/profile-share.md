# 個資分享（WPS）協定與限制

實作在 `src/features/social/profile-share.js`（編碼、分塊、接收組裝）與 `past-profiles.js`（UI、發送）。

## 線路格式（與 Liko-WPS 外掛互通，不可更動）

- Hidden 聊天訊息，Content = `[PROFILESHARE] <shareId> <i>/<n> <chunk>`，i 從 1 起算。
- 所有 chunk 依序串接 = `base64( UTF-8( JSON.stringify(payload) ) )`。
- payload = `{ sharedAt, from: { memberNumber, name }, profile: { memberNumber, name, lastNick, seen, characterBundle } }`。

每塊的大小只由送出端決定，接收端靠 `i/n` 重組，所以送出端可以調整塊大小而不影響互通。

## 送出端

- 每塊大小依 BC 的 `ServerChatMessageMaxLength`（客戶端為 2000）計算：`clamp(上限 - 200, 400, 1800)`；讀不到時沿用舊值 800。
- 沒有「整份 180,000 字元」的上限：那是 BC 單次傳輸資料的限制，分塊後每則訊息各自計算（單則 2000 字元）。
  唯一的送出上限是分塊數 **400 塊**（塊大小 1800 時約 720,000 字元），超過就提示使用者並不送出。
- 分塊經共用的發送預算（`core/send-budget.js`）以**高優先級**依序送出：留給其他訊息的額度是 2（動畫是 4），
  也不因為「別人剛呼叫過 ServerSend」而讓路（表情引擎每秒都會補送）。BC 發送佇列非空仍會等，
  所以聊天最多排在一塊分享後面。額度不足會等待，離開房間或單塊等待超過 10 秒則中止。
- 已知上限：分享與表情共用 BC 同一個 14 則 / 1.2 秒的視窗。以表情每 250ms 送一則的情況模擬，
  120 塊（約 216 KB）約需 19 秒（低優先級約 27 秒）；沒有表情流量時約 12 秒。要再縮短就得減少表情補送或分塊數。
- 同一時間只送一份，進行中再按「分享」會提示稍候。
- 編碼與舊版 `btoa(unescape(encodeURIComponent(...)))` 輸出逐位元相同（測試涵蓋）。

## 接收端（來自房內任何人，視為不可信）

- 單塊以嚴格樣式解析：`i`、`n` 必須是 1 至 400 之間的整數且 `i ≤ n`，shareId 限 `[A-Za-z0-9_-]{1,40}`，單塊 ≤ 2000 字元。
  舊版曾因 `1000000000/1` 讓頁面卡死約一分鐘（用舊版真實處理函式重現）。
- 組裝以「伺服器附的送出者編號 + shareId」為鍵，別人無法往你正在接收的分享插分塊。
- 容量有界：同時組裝 8 份、每位送出者 2 份、單份 ≤ 400 塊 × 2000 字元（800,000，由塊數與塊大小推出）、存活 60 秒。
- 組完後逐欄驗證：成員編號為正整數、名稱為非空字串、`characterBundle` 為 JSON 物件且 `MemberNumber` 與外層一致；`seen` 不得晚於現在。
- 顯示的來源名稱取自伺服器附的送出者，不採用 payload 自稱的名字。
- 組完並驗證通過後**立即記錄**到本機資料庫（與 FCM 一致），不必點「開啟」；只在 `seen` 比本機那份新（或本機沒有）時才覆蓋，自己送出的不再存。點「開啟」時會再呼叫同一個函式，結果相同。

## 尚未驗證

- 伺服器端對 Hidden 訊息長度的實際上限（客戶端常數為 2000，伺服器未在此倉庫）。
- 舊版 WPS 外掛接收較大分塊（最多 1500 字元）時的行為；本專案的接收端不依賴塊大小。
